# 테스트 코드 작성 자동화 평가 기준

이 문서는 Codex 기반 테스트 코드 작성 자동화를 평가하기 위한 기준을 정리한다.  
평가의 목적은 단순히 테스트 코드가 생성되었는지가 아니라, 생성된 테스트가 미리 정의한 시나리오를 얼마나 충족하고, 실제 결함을 얼마나 탐지하며, 개발자 개입 비용을 얼마나 줄이는지 확인하는 것이다.

## 평가 요약

| 평가 항목 | 중요도 | 평가 목적 | 측정 방법 | 판정 기준 | 비고 |
|---|---:|---|---|---|---|
| 시나리오 충족률 | 핵심 | 미리 정의한 테스트 시나리오를 실제 테스트가 얼마나 만족하는지 평가 | 시나리오별 충족 여부 체크 | 시나리오 맥락 일치, 핵심 assertion 포함, 테스트 성공을 모두 만족하면 충족 | 가장 중요한 품질 지표 |
| 테스트 커버리지 증가율 | 보조 | 핵심 로직이 테스트 실행 경로에 얼마나 포함되었는지 확인 | 핵심 로직 기준 line/branch coverage 비교 | 테스트 작성 전후 커버리지 증가분 측정 | 전체 커버리지보다 핵심 로직 기준으로 평가 |
| 결함 탐지력 | 핵심 | 테스트가 실제 결함을 잡을 수 있는지 평가 | mutation testing 또는 의도적 결함 주입 후 탐지 여부 확인 | 결함 탐지, 원인 보고, 정상 코드와 비교, 대안 제시 여부 확인 | 커버리지보다 테스트의 실효성을 잘 보여줌 |
| 테스트 코드 가독성 | 보조 | 사람이 검토하고 유지보수하기 쉬운 테스트인지 평가 | 루브릭 기반 1~5점 평가 | DAMP, mock 최소화, Given-When-Then, 유효한 assertion 기준으로 평가 | 완전 객관 지표는 아니므로 기준을 고정해야 함 |
| 테스트 작성 비용 | 핵심 | 자동화 과정에서 필요한 모델 비용과 개발자 개입 비용을 평가 | 토큰, 호출 횟수, 생성 시간, 검토 시간, 수정량, 개입 시간 기록 | 시나리오 1개 충족당 비용, 개발자 개입 시간 감소 여부 확인 | 포트폴리오에서 자동화 효율을 보여주는 핵심 지표 |

## 1. 시나리오 충족률

개인 프로젝트 특성상 테스트 작성 전에 주요 테스트 시나리오를 미리 정의하고, Codex가 생성한 테스트가 그 시나리오를 얼마나 만족하는지 평가한다.

### 충족 조건

아래 조건을 모두 만족하면 해당 시나리오를 충족한 것으로 본다.

| 조건 | 설명 |
|---|---|
| 시나리오 맥락 일치 | 생성된 테스트가 사전에 정의한 시나리오와 의미상 동일한 동작을 검증하는가 |
| 핵심 assertion 포함 | 해당 시나리오에서 반드시 검증해야 하는 결과값, 상태 변화, 예외, 호출 여부 등을 assertion으로 확인하는가 |
| 테스트 실행 성공 | 생성된 테스트가 실제 테스트 실행 환경에서 성공하는가 |

### 산식

```text
시나리오 충족률 = 충족한 시나리오 수 / 전체 시나리오 수 * 100
```

부분적으로만 만족한 시나리오는 충족률에 포함하지 않고 별도 기록한다.

예시:

| 전체 시나리오 | 충족 | 부분 충족 | 미충족 | 시나리오 충족률 |
|---:|---:|---:|---:|---:|
| 20 | 14 | 3 | 3 | 70% |

## 2. 테스트 커버리지 증가율

커버리지는 보조 지표로 사용한다. 커버리지가 높다고 해서 좋은 테스트라고 볼 수는 없지만, 핵심 로직이 테스트 대상에 포함되었는지 확인하는 데 유용하다.

### 측정 기준

| 항목 | 설명 |
|---|---|
| Line Coverage | 핵심 로직의 코드 라인이 테스트 실행 중 얼마나 수행되었는지 측정 |
| Branch Coverage | 조건문, 예외 분기, 상태 전이 분기 등이 얼마나 검증되었는지 측정 |
| 대상 범위 | Service, 도메인 로직, 상태 전이, 금액 계산, 멱등성, 트랜잭션 처리 등 |
| 제외 대상 | DTO, 단순 getter/setter, config, generated code, 단순 mapper |

### 산식

```text
커버리지 증가분 = 테스트 작성 후 커버리지 - 테스트 작성 전 커버리지
```

예시:

| 대상 | 작성 전 Line | 작성 후 Line | 증가분 | 작성 전 Branch | 작성 후 Branch | 증가분 |
|---|---:|---:|---:|---:|---:|---:|
| PaymentService | 32% | 78% | +46%p | 18% | 71% | +53%p |

## 3. 결함 탐지력

결함 탐지력은 생성된 테스트가 실제로 잘못된 코드를 잡아낼 수 있는지 평가하는 지표다. 커버리지보다 테스트의 실효성을 더 잘 보여준다.

### 측정 방식

| 방식 | 설명 |
|---|---|
| Mutation Testing | 조건문 반전, 반환값 변경, 연산자 변경 등 자동 변이를 만들고 테스트가 이를 잡는지 확인 |
| 의도적 결함 주입 | 개발자가 핵심 로직에 의도적인 결함을 넣고 테스트가 실패하는지 확인 |

### 평가 기준

| 조건 | 설명 |
|---|---|
| 결함 탐지 | 의도적으로 만든 결함 또는 mutant에 대해 테스트가 실패하는가 |
| 결함 보고 | Codex가 실패 원인을 설명할 수 있는가 |
| 정상 코드와 비교 | 결함 코드와 정상 코드의 차이를 설명할 수 있는가 |
| 대안 제시 | 올바른 수정 방향 또는 보완 테스트를 제안할 수 있는가 |

### 산식

```text
결함 탐지율 = 탐지한 결함 수 / 주입한 결함 수 * 100
```

Mutation testing 도구를 사용하는 경우에는 아래 지표를 함께 기록한다.

| 항목 | 설명 |
|---|---|
| Killed Mutants | 테스트가 잡아낸 mutant 수 |
| Survived Mutants | 테스트가 잡지 못한 mutant 수 |
| No Coverage Mutants | 테스트가 실행하지 않은 영역의 mutant 수 |
| Mutation Score | killed mutants / 전체 유효 mutants * 100 |

## 4. 테스트 코드 가독성

테스트 코드 가독성은 주관성이 있으므로 고정된 루브릭으로 평가한다. 단순히 읽기 좋은 코드인지가 아니라, 실패했을 때 원인을 파악하기 쉽고 유지보수 가능한 테스트인지 확인한다.

### 평가 루브릭

각 항목을 1~5점으로 평가한다.

| 평가 기준 | 1점 | 3점 | 5점 |
|---|---|---|---|
| DAMP 원칙 | 테스트 의도가 숨겨져 있고 helper 의존이 과함 | 일부 중복은 있으나 의도 파악 가능 | 테스트 데이터와 검증 의도가 명확하게 드러남 |
| Mocking 적절성 | 불필요한 mock이 많고 실제 검증 대상이 흐려짐 | 주요 외부 의존성은 mock 처리됨 | 외부 의존성만 적절히 대체하고 핵심 로직은 직접 검증 |
| Given-When-Then 구조 | 준비, 실행, 검증 단계가 섞여 있음 | 구조는 있으나 일부 흐름이 불명확함 | 테스트 흐름이 명확하게 구분됨 |
| Assertion 품질 | 의미 없는 assertion 또는 중복 assertion이 많음 | 핵심 결과 일부를 검증함 | 상태, 반환값, 예외, 호출 여부 등 핵심 결과를 명확히 검증 |

### 산식

```text
가독성 점수 = 각 항목 점수 합계 / 평가 항목 수
```

가독성 점수는 보조 지표로 사용하고, 평가자는 동일한 기준으로 모든 라운드를 평가한다.

## 5. 테스트 작성 비용

테스트 작성 비용은 Codex를 사용했을 때 실제로 개발자의 부담이 줄었는지 확인하기 위한 지표다. 포트폴리오에서는 특히 개발자 개입 시간이 중요하다.

### 기록 항목

| 항목 | 설명 | 사용 목적 |
|---|---|---|
| 입력 토큰 | 프롬프트, 코드 컨텍스트, 에러 로그, 커버리지 리포트, 피드백 등 Codex에 전달한 토큰 수 | 모델 사용 비용과 필요한 컨텍스트 양 측정 |
| 출력 토큰 | Codex가 생성한 테스트 코드, 분석, 설명, 수정안의 토큰 수 | 생성 비용과 검토 대상 규모 측정 |
| 모델 호출 횟수 | 작업 완료까지 Codex를 호출한 횟수 | 재시도와 피드백 반복 비용 측정 |
| 전체 생성 시간 | 최초 요청부터 Codex 작업 완료까지 걸린 시간 | 자동 생성 속도 측정 |
| 개발자 검토 시간 | 생성된 테스트를 읽고 품질을 판단하는 데 걸린 시간 | 결과물 검토 부담 측정 |
| 개발자 수정 코드 라인 수 | 개발자가 직접 수정한 코드 라인 수 | 생성 코드의 완성도 측정 |
| 개발자 개입 시간 | 프롬프트 작성, 검토, 피드백, 수동 수정, 최종 확인에 사용한 전체 시간 | 자동화 효율을 판단하는 핵심 비용 지표 |

### 권장 파생 지표

| 파생 지표 | 산식 | 의미 |
|---|---|---|
| 시나리오 1개 충족당 토큰 수 | 전체 토큰 수 / 충족 시나리오 수 | 품질 대비 모델 비용 |
| 시나리오 1개 충족당 개발자 개입 시간 | 개발자 개입 시간 / 충족 시나리오 수 | 품질 대비 사람 비용 |
| 커버리지 1%p 증가당 생성 시간 | 전체 생성 시간 / 커버리지 증가분 | 커버리지 개선 효율 |
| 최종 채택 테스트 1개당 수정 라인 수 | 개발자 수정 라인 수 / 최종 채택 테스트 수 | 생성 코드의 수정 필요도 |

개발자 수정 코드 라인 수는 포맷팅이나 import 정리로 왜곡될 수 있으므로 수정 이유를 함께 기록한다.

## 반복 평가 방식

동일한 코드 범위와 동일한 사전 정의 시나리오를 기준으로 여러 라운드를 수행한다. 라운드마다 피드백 전략을 다르게 적용하고, 평가 기준은 중간에 바꾸지 않는다.

| 라운드 | 목적 | 프롬프트 전략 |
|---|---|---|
| Round 0 | 기본 성능 확인 | "테스트 코드 작성해줘" 수준의 단순 요청 |
| Round 1 | 시나리오 반영 개선 | 사전 정의한 테스트 시나리오와 누락 항목을 피드백 |
| Round 2 | 실행 결과 기반 개선 | 테스트 실패 로그, 커버리지 결과, mutation 결과를 피드백 |
| Round 3 | 품질 개선 | 가독성, mock 사용, assertion 품질에 대한 리뷰 결과를 피드백 |

## 최종 판단 기준

최종적으로는 아래 순서로 평가한다.

| 우선순위 | 기준 | 이유 |
|---:|---|---|
| 1 | 시나리오 충족률 | 사전에 정의한 요구사항을 실제로 검증하는지 확인 |
| 2 | 결함 탐지력 | 테스트가 실제 버그를 잡을 수 있는지 확인 |
| 3 | 개발자 개입 시간 | 자동화가 개발자의 시간을 줄였는지 확인 |
| 4 | 테스트 코드 가독성 | 장기적으로 유지보수 가능한 테스트인지 확인 |
| 5 | 테스트 커버리지 증가율 | 테스트 대상 범위가 충분히 넓어졌는지 보조적으로 확인 |

커버리지 증가는 단독 성공 기준으로 사용하지 않는다. 시나리오 충족률과 결함 탐지력이 낮다면 커버리지가 높아도 좋은 테스트 자동화로 평가하지 않는다.
